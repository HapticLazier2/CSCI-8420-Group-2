Interaction: Alerts (HTTP/S POST)

1. Authenticated Data Flow Compromised  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:An attacker can read or modify data transmitted over an authenticated dataflow.
Justification:[XB] Alerts cross the Remote Host Boundary from the Security Engine to LAPI. Authentication identifies the sender but does not by itself prevent network interception or modification; protected transport such as TLS should provide confidentiality and integrity.

2. Spoofing the LAPI Process  [State: Needs Investigation]  [Priority: High] 

Category:Spoofing
Description:LAPI may be spoofed by an attacker and this may lead to information disclosure by Security Engine (Agent). Consider using a standard authentication mechanism to identify the destination process.
Justification:[XB] The Security Engine sends alerts to LAPI across a trust boundary. An attacker could attempt to impersonate LAPI, so the Agent should authenticate the destination using TLS certificate validation or another appropriate server-authentication mechanism.

3. Potential Lack of Input Validation for LAPI  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:Data flowing across Alerts (HTTP/S POST) may be tampered with by an attacker. This may lead to a denial of service attack against LAPI or an elevation of privilege attack against LAPI or an information disclosure by LAPI. Failure to verify that input is as expected is a root cause of a very large number of exploitable issues. Consider all paths and the way they handle data. Verify that all input is verified for correctness using an approved list input validation approach.
Justification:[XB] Alert data crosses the Remote Host Boundary and enters LAPI from another host. LAPI should validate alert structure, field values, sizes, and other expected constraints before processing or storing the data.

4. Potential Data Repudiation by LAPI  [State: Needs Investigation]  [Priority: Medium] 

Category:Repudiation
Description:LAPI claims that it did not receive data from a source outside the trust boundary. Consider using logging or auditing to record the source, time, and summary of the received data.
Justification:[XB] Alerts cross a trust boundary. Authenticated audit logging should record the sending machine, time, and processing result so receipt and handling of alerts can be traced.

5. Data Flow Sniffing  [State: Needs Investigation]  [Priority: High] 

Category:Information Disclosure
Description:Data flowing across Alerts (HTTP/S POST) may be sniffed by an attacker. Depending on what type of data an attacker can read, it may be used to attack other parts of the system or simply be a disclosure of information leading to compliance violations. Consider encrypting the data flow.
Justification:[XB] Alert information crosses a network trust boundary and may contain sensitive security data. TLS should protect alert contents from disclosure to an attacker observing network traffic.

6. Potential Process Crash or Stop for LAPI  [State: Needs Investigation]  [Priority: High] 

Category:Denial Of Service
Description:LAPI crashes, halts, stops or runs slowly; in all cases violating an availability metric.
Justification:[XB] A compromised or malfunctioning Agent could submit large numbers of alerts or malformed requests and consume LAPI resources. Request limits, input-size limits, timeouts, monitoring, and resource controls should reduce this availability risk.

7. Data Flow Alerts (HTTP/S POST) Is Potentially Interrupted  [State: Needs Investigation]  [Priority: Medium] 

Category:Denial Of Service
Description:An external agent interrupts data flowing across a trust boundary in either direction.
Justification:[XB] Alert delivery crosses a network trust boundary and may be interrupted by an attacker or network failure. Resilient network configuration, appropriate retry behavior, monitoring, and availability controls should reduce loss of alert delivery.

8. Elevation Using Impersonation  [State: Not Applicable]  [Priority: Low] 

Category:Elevation Of Privilege
Description:LAPI may be able to impersonate the context of Security Engine (Agent) in order to gain additional privilege.
Justification:[XB] This threat describes LAPI impersonating the operating-system execution context of the Security Engine Agent. LAPI receives alert data through an API but does not inherit or execute using the Agent&#39;s local security context, so this specific elevation path does not apply.

9. LAPI May be Subject to Elevation of Privilege Using Remote Code Execution  [State: Needs Investigation]  [Priority: High] 

Category:Elevation Of Privilege
Description:Security Engine (Agent) may be able to remotely execute code for LAPI.
Justification:[XB] Alert data is supplied to LAPI from another host. Crafted alert content could potentially exploit a parsing or processing vulnerability, so strict validation, safe parsing, patching, and least-privilege execution are expected controls.

10. Elevation by Changing the Execution Flow in LAPI  [State: Needs Investigation]  [Priority: High] 

Category:Elevation Of Privilege
Description:An attacker may pass data into LAPI in order to change the flow of program execution within LAPI to the attacker's choosing.
Justification:[XB] Untrusted alert data reaches LAPI across a trust boundary. Crafted input could exploit an implementation defect and alter execution flow, so safe input handling, validation, patching, and least privilege should be used.

11. Cross Site Request Forgery  [State: Not Applicable]  [Priority: Low] 

Category:Elevation Of Privilege
Description:Cross-site request forgery (CSRF or XSRF) is a type of attack in which an attacker forces a user's browser to make a forged request to a vulnerable site by exploiting an existing trust relationship between the browser and the vulnerable web site. In a simple scenario, a user is logged in to web site A using a cookie as a credential. The other browses to web site B. Web site B returns a page with a hidden form that posts to web site A. Since the browser will carry the user's cookie to web site A, web site B now can take any action on web site A, for example, adding an admin to an account. The attack can be used to exploit any requests that the browser automatically authenticates, e.g. by session cookie, integrated authentication, IP whitelisting. The attack can be carried out in many ways such as by luring the victim to a site under control of the attacker, getting the user to click a link in a phishing email, or hacking a reputable web site that the victim will visit. The issue can only be resolved on the server side by requiring that all authenticated state-changing requests include an additional piece of secret payload (canary or CSRF token) which is known only to the legitimate web site and the browser and which is protected in transit through SSL/TLS. See the Forgery Protection property on the flow stencil for a list of mitigations.
Justification:[XB] Alert submission is a machine-to-machine API operation rather than a browser-based authenticated session, and authentication does not depend on automatically submitted browser cookies. Traditional CSRF therefore does not apply.

Interaction: Alerts/decisions (SQL write)

12. Spoofing of Destination Data Store CrowdSec DB  [State: Needs Investigation]  [Priority: Medium] 

Category:Spoofing
Description:CrowdSec DB may be spoofed by an attacker and this may lead to data being written to the attacker's target instead of CrowdSec DB. Consider using a standard authentication mechanism to identify the destination data store.
Justification:LAPI depends on the configured CrowdSec DB as the destination for alerts and decisions. If an attacker could redirect or replace the database, security data could be written to an attacker-controlled location. Database location, ownership, permissions, and connection configuration should be protected.

13. Potential Excessive Resource Consumption for LAPI or CrowdSec DB  [State: Needs Investigation]  [Priority: Medium] 

Category:Denial Of Service
Description:Does LAPI or CrowdSec DB take explicit steps to control resource consumption? Resource consumption attacks can be hard to deal with, and there are times that it makes sense to let the OS do the job. Be careful that your resource requests don't deadlock, and that they do timeout.
Justification:Large volumes of alerts or database activity could consume CPU, memory, disk, or database resources and reduce availability. Resource limits, timeouts, monitoring, retention controls, and capacity planning should be evaluated.

Interaction: Log lines (file read)

14. Spoofing of Source Data Store Log Files  [State: Needs Investigation]  [Priority: Medium] 

Category:Spoofing
Description:Log Files may be spoofed by an attacker and this may lead to incorrect data delivered to Security Engine (Agent). Consider using a standard authentication mechanism to identify the source data store.
Justification:Log files are trusted input to the security engine. If an attacker can replace or modify the expected log source, false or misleading events could be processed. File ownership, permission and trusted acquisition configuration should restrict modification of log sources.

15. Weak Access Control for a Resource  [State: Needs Investigation]  [Priority: Medium] 

Category:Information Disclosure
Description:Improper data protection of Log Files can allow an attacker to read information not intended for disclosure. Review authorization settings.
Justification:Log files may contain security-sensitive information. Access should be restricted through filesystem permissions and least privilege so only the Security Engine and authorized administrators can read them.

16. Risks from Logging  [State: Needs Investigation]  [Priority: High] 

Category:Tampering
Description:Log readers can come under attack via log files. Consider ways to canonicalize data in all logs. Implement a single reader for the logs, if possible, in order to reduce attack surface area. Be sure to understand and document log file elements which come from untrusted sources.
Justification:Log lines may contain attacker-controlled or malformed content. Parsers should safely validate and normalize expected fields and reject malformed or unexpected input so crafted log entries cannot abuse log processing.
